1. Aggregate functions

Aggregate functions turn many rows into one summary value.

FunctionReturns
COUNT(*)number of rows
COUNT(column)number of rows where that column is not NULL
SUM, AVGtotal and average of a number column
MIN, MAXsmallest and largest value

Checkpoint 1: predict before you run

SELECT COUNT(*), COUNT(email)
FROM customers;

There are 5 customers. Ethan Moore has no email on file (NULL). What does this return?

COUNT(*) counts every row. COUNT(email) skips NULLs, so Ethan is not counted.

3. Filtering groups with HAVING

WHERE filters rows before grouping. HAVING filters groups after aggregating, so it can use COUNT, SUM and the rest.

Checkpoint 2: predict before you run

SELECT category, COUNT(*)
FROM books
GROUP BY category
HAVING COUNT(*) >= 2;

The 8 books fall into 5 categories: Analytics (1), Database (2), Infrastructure (1), Management (2) and Programming (2). How many rows come back?

Grouping makes 5 rows, one per category. HAVING keeps only groups with 2 or more books: Database, Management and Programming.

4. Changing data: INSERT, UPDATE, DELETE

These statements change the table instead of reading it. Always write the WHERE clause on UPDATE and DELETE first: without it, the change hits every row.

Try it: remove the WHERE line from the UPDATE and run again. Every book gets 10 more copies. In a real database, that mistake reaches production. Your copy here resets on every run.

5. Creating tables with keys

A primary key uniquely identifies each row. A foreign key must match a primary key in another table, which protects the data from orphan rows. NOT NULL makes a column required.

Try it: add INSERT INTO book_authors VALUES (99, 1); before the SELECT. There is no book 99, so the foreign key blocks it. That is the database protecting you.

6. Designing a database: ER diagrams and normalization

Before writing CREATE TABLE, designers sketch an entity-relationship (ER) diagram. Entities become tables, attributes become columns, and relationships become keys.

RelationshipBookstore exampleHow to build it
One-to-many (1:N)One publisher has many booksPut the "one" side's key in the "many" table as a foreign key (books.publisher_id)
Many-to-many (M:N)An order has many books; a book appears in many ordersAdd a junction table with both keys (order_items)

Normalization removes repeated data so each fact is stored once. Here is a badly designed orders table:

Checkpoint 3: spot the problem

In the bad table above, Ana Lopez moves to Plano. What goes wrong?

Storing the same fact in many rows causes an update anomaly. In 3NF, her city lives once in customers, so one UPDATE fixes everything.
